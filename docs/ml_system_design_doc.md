# Дизайн ML системы — LLM Guardrails with AutoML

# 1. Цели и предпосылки

## 1.1. Зачем идем в разработку продукта

### 1.1.1. Бизнес-цель

- Обеспечение требований безопасности LLM за счёт автоматического обнаружения и блокировки вредоносных атак
- Снижение затрат на ручную настройку защитных механизмов для LLM

### 1.1.2. Почему станет лучше от использования ML

- Поиск атак, а также построение защиты от них - ручная и рутинная работа. AutoML позволяет автоматически находить эффективные стратегии защиты (guardrails) против атак на LLM.

### 1.1.3. Что будем считать успехом итерации с точки зрения бизнеса

### Целевая постановка

Целью данной итерации является повышение уровня безопасности LLM за счёт обнаружения и блокировки скрытых атак, которые **не блокируются самой Target LLM**, при строгом контроле деградации пользовательского опыта.

Система рассматривается как **каскад защитных механизмов**, в котором:

* Target LLM обладает встроенным механизмом self-refusal;
* внешние фильтры (Baseline / AutoML Guardrail) расширяют покрытие за счёт обнаружения Blind Spots.

---

### Целевые метрики и ограничения

**Ключевая целевая метрика (Primary Objective):**

* **Recall on Blind Spots**
  Доля вредоносных запросов, которые:

  1. не были заблокированы Target LLM (self-refusal = false),
  2. но были успешно обнаружены и заблокированы внешним guardrail-механизмом.

Данная метрика отражает **реальную добавочную ценность системы**, поскольку детекция очевидных атак уже обеспечивается базовой моделью.

---

**Жёсткое бизнес-ограничение (UX Constraint):**

* **False Positive Rate (FPR)**
  Доля безопасных запросов (**Naturally Allowed**), которые были ошибочно заблокированы каскадом защитных механизмов.

FPR интерпретируется как **бюджет на деградацию пользовательского опыта**:

* рост FPR приводит к «параноидальному поведению» системы,
* снижает полезность Target LLM,
* и напрямую влияет на продуктовую применимость решения.

---

### Калибровка и baseline

* **Anchor Point (Baseline 1):**

  * Векторный фильтр (KNN) калибруется таким образом, чтобы итоговый **FPR каскада составлял 5%**.
  * Это значение фиксируется как допустимый UX-бюджет для данной итерации.
* **Сравнение AutoML Guardrail с Baseline 1:**

  * AutoML-стратегия считается успешной, если:

    * при **том же уровне FPR (≤ 5%)**
    * достигается **значимый прирост Recall on Blind Spots**.

---

### Динамический критерий успеха итерации

Итерация считается успешной, если выполняются одновременно следующие условия:

* **Recall on Blind Spots ≥ 0.70**
* **FPR ≤ 5%**
* Система демонстрирует устойчивое поведение на независимой тестовой выборке.

---

### Сегментное понимание качества

Качество системы оценивается дифференцированно по следующим сегментам:


| Сегмент        | Определение                                          | Ожидаемое поведение                                |
| ----------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Obviously Refused** | Атаки, заблокированные Target LLM           | Сохранение отказа                                    |
| **Blind Spots**       | Атаки, пропущенные Target LLM                   | Обнаружение guardrail (Recall ≥ 0.7)                     |
| **Naturally Allowed** | Безопасные запросы                             | Пропуск пользователю                              |
| **Paranoid Refusals** | Ошибочные блокировки benign-запросов | Минимизация (контролируется через FPR) |

### 1.2.2. Бизнес ограничения

- Для обеспечения интерактивного пользовательского опыта и возможности интеграции в production-контуры, система должна соответствовать следующим технологическим рамкам:
- Производительность (Latency):
- - Целевой показатель (Target): P95 latency инференса ≤ 100 мс.

- - Масштаб данных: Оптимизация проводится на выборке из 10000 промптов, что является достаточным для формирования специфичной политики безопасности в рамках итерации.

## 2.3. Этапы решения задачи Data Scientist

### 2.3.1. Этап 1

На данном этапе проводится подготовка данных и формирование стратегии обучения, ориентированной на сложные кейсы, для оптимизации работы LLM-фильтра.

#### 2.3.1.1. Данные и сущности:

- Используемый датасет: wildguardtrain (hardcrafted+autogenerated).
- Основная сущность: text (входной промпт).
- Целевая переменная: label ∈ {0, 1}, где 1 — вредоносная атака (attack), 0 — безопасный запрос (benign).
- Объем выборки: Для итерации AutoML извлечено 10000 строк для обучения, 4000 строк для подбора гиперпараметров и 10000 строк для теста.

#### 2.3.1.2. Инсайты из EDA и проблемы:

- Семантическое разделение: Проекция PCA демонстрирует значительное смешивание классов в центре распределения. Это подтверждает, что простые статистические методы («счетчики») не обеспечивают надежной защиты, и использование LLM оправдано для анализа контекста.
- Вариативность длин: Анализ распределения длин слов (Wordcount) показал отсутствие единого шаблона длины для атак, что делает простые эвристики неэффективными.

#### 2.3.1.3. Риски и конфиденциальность:

- Конфиденциальность: Атаки могут содержать чувствительную или приватную информацию, что требует осторожности при логировании.

#### 2.3.1.4. Результат этапа:

- Подготовленные файлы данных не-adversarial сложности.
- Ноутбук EDA с визуализациями (PCA, Wordclouds), подтверждающий репрезентативность выборки для обучения «умного» пре-фильтра.

#### 2.3.1.5. Критерии качества результата этапа:

- Корректность разметки: Баланс классов должен быть близок к ориентировоч (Attack/Benign) для предотвращения смещения модели в сторону параноидального поведения.
- Валидационная чистота: Тестовая выборка (10000 строк) должна быть строго отделена от обучающей и содержать аналогичное распределение по классам.

#### 2.3.1.6. Периодичность обновления датасета:

Для поддержания высокого качества фильтрации и адаптации к новым типам атак (Zero-day Jailbreaks), установлены следующие регламенты:

- Плановое обновление: 1 раз в квартал. Проводится полная переоценка модели на свежих данных из открытых бенчмарков и внутренних логов.

- Оперативное обновление (Hotfix): Внеплановое дообучение инициируется при обнаружении новых критических уязвимостей или падении метрики Recall ниже порога 0.85.

- Архивация: Устаревшие данные (старше 12 месяцев) переносятся в архив, чтобы избежать «засорения» модели неактуальными паттернами общения.

#### 2.3.1.7. Процесс получения и загрузки данных:

Процесс автоматизирован и включает в себя несколько этапов контроля качества:

- Сбор (Acquisition):

- - Внешние источники: Парсинг и интеграция обновлений из репозиториев (например, новые версии WildGuard или JailbreakBench).

- - Внутренние логи: Анонимизированные логи запросов, которые были помечены системой мониторинга как «подозрительные», но пропущены фильтром (False Negative).

- Очистка и деидентификация:

- - Автоматическое удаление PII (персональных данных) с помощью регулярных выражений и специализированных NER-моделей перед попаданием в обучающую выборку.

### 2.3.2. Этап 2

Разработка и валидация систем фильтрации (Baseline & MVP). На данном этапе реализуется иерархическая структура классификации и проводится оптимизация GuardRails.

#### 2.3.2.1. Архитектура решения (Model Zoo)

- Target LLM (Защищаемый объект)
- - Модель: Qwen 2.5 0.5B (Instruct-версия).
- - Роль: Основная модель, выполняющая задачи пользователя. Она обладает встроенным механизмом «Self-refusal» (безопасность на уровне весов), который используется как Baseline 0 для замера эффективности системы.
- Judge LLM (Решает просочилась ли атака) Модель: Qwen 2.5 1.5B (Instruct-версия).
- - Роль: Модель, которая ревьют промпт-ответ из TargetLLM, и определяет попала ли она под влияение пользователя, либо же штатно отказалась.
- Baseline 1: Векторный фильтр (KNN)
- - Данный слой предназначен для мгновенной детекции простых и часто встречающихся атак на основе семантического сходства.

#### 2.3.2.2. Методология оценки (Evaluation Framework)

##### Общая постановка оценки

Цель evaluation — сравнить различные стратегии защиты (prompt-based, retrieval-based) в рамках **изолированного guardrail-модуля**, применимого к любому downstream Target LLM, включая агентные системы с высоким потреблением ресурсов.

Target LLM **не является частью оцениваемой системы** и используется исключительно как **reference baseline** для аналитической сегментации данных и интерпретации результатов.

Оценка проводится на фиксированной тестовой выборке, включающей:

* benign запросы,
* вредоносные запросы, приводящие к self-refusal Target LLM (*Obviously Refused*),
* вредоносные запросы, на которые Target LLM отвечает небезопасно (*Blind Spots*).

---

##### Роль Baseline 0 (Target LLM)

Baseline 0 представляет собой прогон тестовой выборки через Target LLM без использования guardrail.

Он используется **исключительно для анализа**, а именно:

* для разбиения вредоносных запросов на сегменты:

  * *Obviously Refused*,
  * *Blind Spots*;
* для оценки дополнительной ценности guardrail поверх встроенных safety-механизмов Target LLM.

Baseline 0:

* **не участвует в предсказании**,
* **не используется в каскаде принятия решений**,
* **не влияет на обучение или AutoML-оптимизацию**

---

##### Основные и диагностические метрики

###### Primary business metric

* **Recall on Blind Spots**
  Доля вредоносных запросов, которые:

  * не были заблокированы Target LLM,
  * но были корректно обнаружены и заблокированы guardrail.

Данная метрика отражает **ключевую бизнес-ценность текущей итерации** — снижение остаточного риска для пользователей, не покрытого safety-механизмами Target LLM.

---

###### Operational metric

* **Recall (All Attacks)**
  Доля всех вредоносных запросов (включая *Obviously Refused* и *Blind Spots*), заблокированных guardrail.

Метрика отражает способность guardrail предотвращать:

* опасные ответы,
* **ненужные и потенциально дорогие вызовы Target LLM**.

---

###### Constraint metrics

* **False Positive Rate (FPR)**
  Доля benign-запросов, ошибочно заблокированных guardrail.

FPR рассматривается как жёсткое ограничение, так как:

* напрямую влияет на пользовательский опыт,
* ограничивает полезность downstream LLM.
* **Latency (P95)**
  95-й перцентиль времени инференса guardrail.

Latency является критичным системным ограничением, особенно в сценариях использования guardrail совместно с агентными или multi-step LLM-системами.

---

##### Использование метрик в AutoML

AutoML-процедура оптимизирует стратегии защиты на обучающей выборке (200 примеров) с учётом следующих принципов:

* целевая оптимизация направлена на максимизацию **Recall (All Attacks)**,
* при соблюдении заданных порогов по:
  * FPR

Метрика **Recall on Blind Spots**:

* не используется напрямую в objective AutoML,
* применяется как **диагностический и сравнительный показатель** при финальной оценке стратегий на тестовой выборке.

---

##### Итоговая интерпретация результатов

Финальное сравнение стратегий защиты проводится на тестовой выборке и включает:

* сравнение по Recall on Blind Spots (основной KPI итерации),
* анализ общего Recall как индикатора resource protection,
* проверку соблюдения ограничений по FPR и Latency,
* интерпретацию trade-off между безопасностью, пользовательским опытом и вычислительными затратами.

---

#### 2.3.2.3 Baseline 1: Векторный фильтр (KNN)

##### Назначение и роль в системе

Baseline 1 представляет собой **быстрый и детерминированный pre-filter**, предназначенный для:

* блокировки **очевидных и часто повторяющихся атак**,
* снижения нагрузки на downstream Guardrail LLM,
* формирования **якорной точки сравнения** для оценки AutoML-подхода.

Данный baseline реализует **простую retrieval-based стратегию**, не использующую генеративные возможности LLM и не анализирующую скрытое намерение пользователя.

---

##### Архитектура и параметры

* **Эмбеддер:** `sentence-transformers/all-MiniLM-L6-v2` (Sentence-Transformers)

  * Размерность: 384
  * Контекстное окно: до 256 токенов
* **Индекс:** k-nearest neighbors (KNN) - KNeighborsClassifier из sklearn
* **Метрика расстояния:** cosine similarity
* **Источник базы:** обучающая выборка (10000 промптов), включающая как attack-, так и benign-примеры

---

##### Логика принятия решения

Для входного промпта вычисляется эмбеддинг, после чего извлекаются 20 примеров (подборано через TPE) из обучающего набора.
 
* Если probability ≥ threshold → промпт классифицируется как **attack** и блокируется.

---

##### Калибровка порога (Threshold selection)

Порог similarity подбирается **на валидационной части обучающей выборки** с целью:

* обеспечить **False Positive Rate (FPR) ≤ 5%**,
* зафиксировать допустимый UX-бюджет для сравнения стратегий.

Таким образом, Baseline 1 используется как **anchor point**:

* все последующие стратегии (включая MVP) сравниваются **при сопоставимом уровне FPR**.


### 2.3.3. MVP: Двустадийная AutoML оптимизация Guardrail

На данном этапе система переходит от фиксированного базового решения к автоматизированному подбору архитектуры и гиперпараметров. Используется каскадная логика фильтрации для достижения баланса между полнотой детекции и сохранением UX.

#### 2.3.3.1. Архитектура каскада (Policy Module)
Система представляет собой последовательный фильтр из двух стадий:
1.  **Stage 1 (Primary Filter):** Грубая классификация на широком наборе признаков. Цель — захватить максимум потенциальных атак.
2.  **Stage 2 (Refinement Filter):** Обучается только на тех примерах, которые Stage 1 пометил как «атака». Цель — снизить количество ложных срабатываний (FPR), «отсеивая» безопасные запросы, вызвавшие подозрение на первом этапе.

**Логика принятия решения:**
* Если $Score_{stage1} < T_1 \rightarrow$ **Пропуск (Benign)**.
* Если $Score_{stage1} \ge T_1$ И ($Score_{stage2} \ge T_2$ ИЛИ Stage 2 отсутствует) $\rightarrow$ **Блокировка (Attack)**.

#### 2.3.3.2. Пространство поиска AutoML (Search Space)
Для оптимизации используется фреймворк **Optuna** с алгоритмом **TPE (Tree-structured Parzen Estimator)**.

* **Набор моделей:** Logistic Regression, Linear SVC, KNN, CatBoost, SVC (RBF), MLP.
* **Генерация признаков (Feature Engineering):**
    * *Embeddings:* Семантические векторы (`all-MiniLM-L6-v2`).
    * *Anomaly Score:* Результаты Isolation Forest для поиска статистических выбросов.
    * *Centroid Margin:* Расстояние до центроидов классов в векторном пространстве.
    * *Статистика:* Длина промпта, POS-теги, вхождение ключевых слов.
* **Препроцессинг:** Автоматическое переключение использования `StandardScaler`.

#### 2.3.3.3. Алгоритм оптимизации
Процесс разбит на два последовательных цикла (Study):

**Шаг 1: Оптимизация Stage 1**
* **Objective:** Максимизация **Recall** при жестком ограничении $FPR \le 15\%$ (целевое значение для первого слоя).
* Результат: Лучшая модель первого слоя, набор признаков и порог $T_1$.

**Шаг 2: Оптимизация Stage 2**
* **Objective:** Минимизация **FPR** (максимизация $1 - FPR$) при условии сохранения Recall на уровне не ниже $95\%$ от Recall первой стадии.
* Обучение проводится строго на подмножестве данных, классифицированных Stage 1 как атаки.

#### 2.3.3.4. Метод калибровки порогов
Вместо стандартного порога $0.5$ используется **Grid Search по перцентилям** скоров моделей на валидационной выборке. Это позволяет:
* Находить пороги даже для моделей, не выдающих вероятности напрямую (например, `Decision Function` в SVM).
* Точно вписываться в бизнес-ограничения по FPR (UX-бюджет).

#### 2.3.3.5. Оценка и валидация
Итоговая стратегия (модели + признаки + пороги) фиксируется и проверяется на независимой тестовой выборке по сегментам:
* **Overall Metrics:** Общая точность системы.
* **Blind Spots Metrics:** Эффективность именно на тех атаках, которые пропускает Target LLM.

# 3. Подготовка пилота
## 3.1. Способ проведения пилота
Пилотный запуск будет реализован в виде интеграционного прокси-слоя между пользователем и Target LLM. Процесс разделен на два этапа:

- Режим «Тень» (Shadow Mode): Система Guardrails анализирует входящие промпты параллельно с основным потоком, но не блокирует их. Ответы системы и решения классификатора логируются для оценки FPR на реальном трафике без влияния на UX.

- Режим «Активная фильтрация»: При достижении стабильных метрик в режиме «тени», система переключается в режим блокировки. Входной промпт проходит через каскад (Stage 1 -> Stage 2). Если система определяет атаку, пользователю возвращается стандартный шаблон отказа, а вызов дорогостоящей Target LLM отменяется для экономии ресурсов.

## 3.2. Способ оценки успешности
Успешность пилота определяется достижением целевых показателей на независимом тестовом наборе (10 000 строк) и подтверждением в условиях реальной нагрузки.

Ключевые критерии (Acceptance Criteria):

- Эффективность детекции: Recall на сегменте Blind Spots (атаки, пропущенные встроенной защитой Qwen 2.5 0.5B) должен быть ≥0.70.

- Сохранение UX: Итоговый False Positive Rate (FPR) каскада на безопасных запросах (Naturally Allowed) не должен превышать 5%.

- Производительность: 95-й перцентиль времени обработки запроса (P95 Latency) ≤100 мс.

Автоматизация: Успешное проведение хотя бы одного полного цикла AutoML (TPE оптимизация) в течение 24 часов при появлении новых паттернов атак.

Для верификации решений используется Judge LLM (Qwen 2.5 1.5B), которая оценивает, действительно ли пропущенный промпт привел к нарушению политик безопасности в ответе Target LLM.

## 3.3. Подготовительные шаги
Для запуска пилота необходимо выполнить следующие действия:

Заморозка артефактов: Фиксация весов моделей Stage 1 (SVC) и Stage 2 (KNN), а также конфигурации признаков (embeddings, POS-теги) и порогов.

# 4. Внедрение
## 4.1. Архитектура технического решения
Система внедряется как прокси, который перехватывает запросы к Target LLM.

Компоненты системы:

- Guardrail Service (Python/FastAPI): Легковесный микросервис, реализующий логику каскада.

- Feature Store (In-memory): Кэш для эмбеддингов часто встречающихся промптов.

- Model Storage (S3/MLflow): Хранилище для весов SVC, KNN и IsolationForest.

## 4.2. Инфраструктура
Среда: Kubernetes (K8s) кластер.

Compute: * CPU: 2 ядра (минимум) для базовой логики и KNN.

GPU: NVIDIA T4 или аналогичная (желательно) для ускорения all-MiniLM-L6-v2 при высоком RPS.

Память: 4 ГБ RAM (основной объем занимает модель эмбеддингов и индекс KNN).

## 4.3. Требования к надежности и быстродействию
- Быстродействие:

- - Target Latency (P95): < 100 мс.

- - Оптимизация: Использование квантованной модели эмбеддингов (INT8) и библиотеки Faiss вместо sklearn.KNN для сокращения времени поиска.

- Надежность и масштабирование:

- - Масштабирование: Horizontal Pod Autoscaler (HPA) по метрике CPU/Latency. При превышении 80 мс на P95 — деплой дополнительных реплик.

- - Fail-safe: В случае недоступности сервиса Guardrails, система по умолчанию блокирует (Fail-Closed) или пропускает (Fail-Open) запрос в зависимости от критичности контура безопасности.

## 4.4. Результаты нагрузочного тестирования
